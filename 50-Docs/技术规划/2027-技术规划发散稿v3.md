# 2027 技术规划方向发散稿 v3（内部讨论版）

> 定位：发散不定论，内部务虚讨论用
> 前版：v2（2026-11-06 结对共创），本版在其基础上补论证、补依据、补风险，结构不变
> 目标读者：AI辅助研发部门内部

## 核心结论（先说答案）

- 2027 的核心 reframing：**从"让人写全"到"让Agent配全"**。规划不再假设输入完备，而是把"配齐上下文"本身变成平台能力。
- 不单押一个场景：做**平台级横向能力（方向1/2/4/5）+ 多部门薄试点并行**，主线仍是闭环2联邦互联（方向3）。
- 5+1 个方向按"先可观测、再配准、后全自动"排序，全自动的前提是熔断和计费先就位（方向5是方向4的前置）。

---

## 一、共识回顾（已对齐）

- 部门定位：AI辅助研发 —— AI Coding / AI Native工作台 + 算力 + 知识 + 运维安全
- 规模：200+ → 年中1000 → 年底2000；月均1.3万亿 token，明年起 token 收费
- 主线：多系统联通，闭环2（需求→代码→测试→缺陷），**只连不改**
- 网络：大网→小网单向可传，小网→大网不通，小网内闭环推理
- 现状：SDD + Agent Teams 已在用；模板按场景分（前端/数据库/编解码等）；单测覆盖尚可但多由代码反推生成
- 愿景：除极个别决策外全自动闭环，少人工介入

## 二、本轮新增共识（关键）

1. **不厚此薄彼**：不同部门有各自典型场景，2027 不单押一个场景，做平台级横向能力 + 多部门薄试点并行。
2. **知识有，但不会配**：编程规范/架构规约/接口规范/吞吐量纲/问题案例都在库里，难点在开发过程中**不知道怎么匹配、获取和消费**——是配准问题，不是治理问题。
3. **不逼人写全设计**：设计文档可以要求写，但不能要求事无巨细。规划必须接受"输入永远不完备"这个前提。

=> 2027 核心 reframing：**从"让人写全"到"让Agent配全"**。

### 为什么是这个 reframing（补论证）

- 三个新增共识指向同一个矛盾：人侧输入的边际成本越来越高（写全设计、答全需求），而知识库里的存量知识消费率很低。继续加码"让人写全"会遭遇执行阻力，且与"全自动闭环"的愿景方向相反。
- "让Agent配全"把负担从人转移到平台：配准做好了，token 少烧（少重试）、轮次变少（少澄清）、全自动才有可信输入。它同时是效能问题和成本问题。

## 三、2027 可行方向（5+1）

### 取舍逻辑总览

先说"做什么"的排序原则，和"不做什么"：

| 原则 | 说明 |
|---|---|
| 先可观测，后自动化 | 没有账本（方向5）之前放开全自动（方向4）等于盲飞，所以5是4的前置 |
| 只连不改 | 闭环2坚持 Connector + ID 映射，不动存量系统内部，降低协调成本和风险 |
| 任务驱动，不做全量治理 | 知识治理按场景包渐进，不做10万条全量治理（讨论题1，见第六节） |
| 平台横向 + 试点纵向 | 能力做成横向（所有部门可复用），验证靠各部门薄试点，避免押注单一场景 |

明确**不做**的：全量知识治理、改造存量系统内部逻辑、要求设计文档事无巨细、小网到大网回传。

### 方向1：任务-知识路由器（解决"怎么配"）

- **输入/输出**：输入 = 任务类型 + 场景标签 + US/代码上下文；输出 = 本次必读知识清单（规范X条 + 案例Y个 + 接口Z个），带引用标注。
- **做法**：场景知识包标准化（每包 = 热知识 + 硬约束 checklist），不做全量治理；工作台埋点回流（调了啥、有用否），持续调参。
- **价值**：直接对应共识2"知识有但不会配"，是 reframing 的第一落点；也是方向2（注入什么）和方向4（校验依据）的供给方。
- **KPI**：知识一次配准率（首轮配对即含关键规范的占比）；噪声引用率下降；人均 token -30%。
- **KPI 依据与风险**：token -30% 的逻辑是"配准 → 少重试/少无效生成"，目前缺基线，**Q1 先建 50 US Eval 基线再谈降幅**；若基线测出重试占比低于预期，该目标需下调。配准率靠人工标注抽样校验，前期抽检成本要预留。
- **依赖**：工作台埋点（方向5可复用同一套）。

### 方向2：隐式约束自动注入（接受输入不完备）

- **做法**：人只写关键差异，通用约束由 Agent 从规约自动补：编码规范/架构红线/接口版本/吞吐量纲默认值。需求完整性门禁：生成前一次性问 3-5 个结构化问题，之后不为需求返工。
- **价值**：把"输入不完备"从风险变成设计假设；与方向1构成"配准→注入"链路。
- **KPI**：需求一次澄清通过率；平均轮次 30→12。
- **KPI 依据与风险**：30→12 意味着砍掉 ~60% 轮次，前提是结构化门禁真能前置暴露大部分歧义；建议先按 30→18 设保底目标，12 作为挑战值。注入错误约束（把不适用规范灌进去）是新风险，需方向1的引用标注来兜底可追溯。

### 方向3：闭环2联邦互联（主线）

- **做法**：Q1 需求-代码，Q2 补测试-缺陷，全小网 Connector + ID 映射，引用可追溯。
- **价值**：这是已对齐的主线，多系统联通是一切闭环的物理基础；"只连不改"控制了对存量系统的侵入。
- **KPI**：跨系统引用准确率；一次 Accept 率 15%→35%。
- **KPI 依据与风险**：15% 的现状基线需在 Q1 Eval 中固化为可复现的测量口径（同一批 US 复跑）；35% 意味着翻倍以上，主要杠杆来自方向1/2/4 的输入质量和校验质量，**本方向自身只解决"连得上、溯得回"**，不宜独立承诺翻倍。

### 方向4：设计驱动的独立校验（全自动的裁判）

- **做法**：测试 Agent 从 US/设计**正推**验收用例，与代码 Agent 异源制约，解决"代码反推单测自证满分"；人只裁决两者冲突点。
- **价值**：全自动闭环的可信度来源。没有独立裁判，"全自动"只是"全速出错"。
- **KPI**：设计驱动用例占比；全自动闭环率（简单→中等任务外推）。
- **风险与安全边界**：异源制约会暴露大量冲突，需设定冲突裁决 SLA，避免人成为新瓶颈；全自动范围的扩张必须渐进（简单任务 → 中等任务），且**依赖方向5的熔断先就位**——超步数/超预算必须能拦得住，才谈得上放开边界。

### 方向5：Token 可观测 + 计费 + 熔断

- **做法**：任务/轮次级账单 + 场景配额 + 超步数/超预算熔断（防全自动失控更烧）。
- **价值**：三重身份——收费分摊的账本、失控的刹车、效能证明（省人天 vs 花 token）的数据源。**它是方向4的前置，也是明年 token 收费的基础设施**，优先级应据此理解。
- **KPI**：Top 烧钱归因 100%；失控拦截 100%。
- **KPI 依据与风险**："归因100%"指 Top N 任务/场景的 token 消耗可完整归因到发起方，不是全量归因；"拦截100%"以熔断规则覆盖所有自动化执行路径为口径（含 Agent Teams 子任务），需与方向6审计链打通验证。

### 方向6（底座）：单向供给链 + 运维安全

- **做法**：大网→小网月度镜像同步 + SBOM + 白名单；小网权限隔离 + 全链审计。
- **价值**：网络单向约束下模型/依赖供给的唯一通道；也是安全合规的底线。
- **KPI**：同步 SLA；0 事故。

### 方向依赖关系（一图流）

```
方向6 供给链（底座）
  └─ 方向3 闭环互联（物理基础，主线）
       ├─ 方向1 知识路由器 ──供给──→ 方向2 隐式注入
       │        └────────供给──→ 方向4 独立校验（裁判）
       └─ 方向5 可观测+计费+熔断 ──前置──→ 方向4 全自动放开
```

## 四、倒排（年中1000）

- **Q1**：可观测 + 路由器 MVP（覆盖 2-3 个部门各 1 类模板）+ 需求-代码试点 + 50 US Eval 基线
- **Q2**：隐式注入 + 设计驱动用例推广 + 闭环补全，承接收费，冲 1000 人
- **H2**：计费分摊 + 供给常态化 + 效能证明（省人天 vs 花 token），冲 2000 人

### 排期的资源假设与风险（补论证）

- Q1 同时启动"可观测 + 路由器MVP + 需求-代码试点 + Eval基线"四件事，是全计划最挤的季度。**建议明确：Eval 基线是其余三件的度量前置，优先保**；路由器 MVP 只做 2-3 个部门各 1 类模板，明确砍掉其余场景。
- 年中 1000 人意味着用户规模 5 倍于现在，Q2 承接收费的同时做隐式注入+用例推广，运营压力大。收费分摊机制（讨论题3）若 Q1 末不能定，方向5的计费分摊设计会被阻塞，**这是排期上最大的单点依赖**。
- 2000 人阶段的主要风险不是功能而是**效能证明**：如果 H2 拿不出"省人天 vs 花 token"的可信对比，扩规模的正当性会被挑战。Eval 基线（Q1）在这里第二次兑现价值。
- 建议内部先明确各方向的人力盘子（哪怕粗粒度：平台组/试点组/运维安全组），否则 5+1 并行的资源冲突会在 Q2 集中爆发。

## 五、全自动闭环的安全性（专节加固）

这是愿景里最容易被挑战的部分，单独论证：

1. **刹车先于油门**：方向5的熔断（超步数/超预算）是方向4全自动放开的前置条件，不满足则不扩边界。
2. **异源制约**：代码 Agent 与测试 Agent 从不同来源（代码 vs US/设计）出发互相制约，避免"自己出题自己批卷"。
3. **白名单留人**：建议先固定 3 类必须人工决策——接口 breaking change / 数据删除 / 上线（讨论题2）。
4. **可追溯**：闭环2的 ID 映射 + 方向6全链审计，保证任何一次自动决策可以回放归因。
5. **渐进外推**：全自动闭环率只在简单任务验证后向中等任务外推，不直接跳复杂任务。

## 六、给领导的讨论题（3个）

1. **是否接受"不做全量治理，只做任务驱动的配准"？**（快见效 vs 洁癖）
   - 附内部建议：倾向任务驱动。全量治理在 10 万级知识量下周期长、见效慢，且与"年中1000人"节奏冲突；任务驱动的配准可以在 Q1 就出 MVP 数据，错了可回调。
2. **全自动的边界：哪些决策必须留人？**（建议先白名单 3 类：接口 breaking change / 数据删除 / 上线）
   - 附内部建议：白名单宁少勿多，先跑起来，靠方向5的审计数据再动态增删。
3. **Token 收费分摊机制：平台统付还是产品线分付？**（决定方向5优先级）
   - 附内部建议：分付才能让"Top烧钱归因100%"有人看、有人管；若定统付，方向5降级为纯可观测工具，计费/配额部分可缓。**此题 Q1 末必须定**，否则阻塞 Q2。
