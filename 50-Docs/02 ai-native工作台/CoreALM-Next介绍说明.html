COREALM-NEXT · 介绍说明

CoreALM-Next 是什么

产业装备部建设的研发作业平台。它把现有的作业系统、Agent Teams、公司模型服务和池化资源接到一起，研发人员在同一个工作台里做任务协同、复用资产、跑 AI 执行、看用量，并把用出来的经验沉淀成下一轮能用的东西。

01概述

现状是：需求在 CoreALM、测试设计在专业系统、脚本和构建又各归各家，AI 辅助作业大多零散使用，过程没有留痕，好坏说不清。CoreALM-Next 要解决的就是把这个过程管起来。平台提供五块能力：

任务协同跨系统任务关联、待办与进展汇总；业务事实仍在来源系统
资产复用Skill、Workflow、SOP 等有版本、有证据、可派生
执行记录AI 与人工的全过程留痕，可双向追溯
用量分析Token / Credit 三侧去重统计、多维分析
持续改进候选、验证、发布、观察、回退，一套流程走完
平台不替代任何来源系统。需求、任务、代码的状态仍归原系统持有，平台维护的是关联、配置、执行和分析记录，对外操作都以来源回执为准。

02工作空间怎么建

按业务范围（产品 / 服务 / 版本）组织，配单父级的空间树和订阅机制，不按用户团队拆。

基本规则

  • 一个空间可以关联多个产品、服务、版本对象；同一个对象也可以被多个空间用，跨产品、跨服务的作业不用另建体系。
  • 关联对象从同步目录里选，不手填地址。成员可以提议，空间管理者确认后生效，范围外的对象置灰。
  • 要用别的空间的资产，走订阅。订阅不等于权限——读取和装载始终按发起用户的实际授权校验。
  • 状态只有"使用中"和"已归档"两种。归档保留关联和历史，恢复要审批；有没跑完的执行时不允许归档。空间可以迁移，先预览差异，身份和历史都保留。

几个容易问的问题

  • 上游改了配置，我会不会被动跟着变？不会。父空间更新只提示差异，子空间确认后才采用，可以逐项处理，本地覆盖保留。
  • 为什么不在平台里重建一份产品数据？同一事实只能有一个写入方。来源系统的数据平台只引用，避免两边对不上。
  • 空间是干嘛用的？它是范围和配置的生效边界——任务关联、知识装配、AI 执行都只在这个范围里工作。

03小队 / Skill 等资产怎么管版本、怎么同步

Agent 配置、Skill、Workflow、场景 SOP、上下文模板、装配策略、构建验证配置，统一登记，统一走版本生命周期。

版本怎么管

  • 发布的版本不可修改，有问题走新版本。想正式发布，必须带上这个版本的试用或评测证据，审核人和提交人不能是同一个人。
  • 定制可以派生：派生版保留和上游的差异。上游更新了只提示差异，要不要合入由维护者定，合入后是新草稿、重新审核，不会自动覆盖定制。
  • 不是所有知识都要走这套流程。SPEC、文档这类普通知识，来源系统的原生修订和评审回执就是依据；只有要发布给他人复用的 Skill、SOP、策略，才进完整的发布生命周期。

更新怎么同步

  • 来源改了、删了、撤权了，平台会观察到变化，把受影响的索引和摘要标记为待更新或不可用，未授权的读取直接被挡掉，同时给相关人生成复核待办。
  • 正在跑的执行不受影响，继续用开始时的条件；确实要换条件，就显式派生一个新基线，不静默切换。
  • 每次执行都会冻结一份清单（ContextManifest）：用了哪些知识修订、哪个装配策略版本、实际装载了什么、中间有什么变化。"准备装载"和"实际装载"分开记，事后能还原当时现场，不用靠猜。
  • 空间要采用资产的新版本，同样是先看差异、确认后生效。

04规范化、可度量、可扩展、可进化

这四个词各有一套具体机制在支撑，不是宣传语。

规范化

  • 跨系统的任务按 SR 编号等业务属性关联。关联规则和人工修正都要审核，批过的人工修正不会被后续重算覆盖。
  • 场景 SOP 模板化：必选步骤删不掉，可选步骤按项目裁剪，确认后就是本次流程依据。
  • 资产发布、知识固化、改进发布与回退，统一在一个裁决面处理，等待裁决的事项进个人待办队列。
  • 质量检查分"必须满足"和"建议改进"两档，必选项没过或缺证据，就发不出去、结果确认不了。走例外要写清理由、范围、有效期并审批，原来的"未通过"记录不改写。

可度量

  • 执行过程逐条追加留痕：做了什么步骤、调了什么、人工在哪介入、产出了什么、实际用了哪些知识。
  • Token / Credit 在执行端、产业网关、公司侧三处各留原始记录，对账去重，缺的和对不上的单独列出来，不充数。
  • 分析可以按产品、空间、需求、资产版本、模型切片比较任务量、返工、人工介入、耗时、消耗，点进去能看到证据。
  • 指标口径带版本，算的什么、覆盖哪段、截止到什么时候都写明。

可扩展

  • 新团队、新业务建个子空间就能继承配置；要用现成资产，订阅即可。
  • 定制靠派生，不改写上游；多个资产可以打包锁定整体版本。
  • 外部系统一个一个接：每个系统的接入范围、字段映射、同步、回执单独登记建设，不要求对方改造。
  • 同一事实只有一个写入方，新增能力靠挂接，不动既有职责。

可进化

  • 分析发现的线索、任务里提炼的经验，先进"候选"，有人立项才启动验证。系统只提议，不自己生效。
  • 改进事项走：问题候选 → 人工立项 → 评测验证 → 审核发布 → 上线观察 → 回退或继续。发布成功只说明上线了，观察达标才算改进成功。
  • 评测控制变量：先只加版本/状态约束，再加片段装配，再试单个增强项；任务、模型、环境、标准固定，不把一揽子改动说成单项收益。
  • 授权案例脱敏、标注、人工入集，冻结成版本化数据集；验证集滚动更新，避免对着同一批题刷分。

05一次作业从头到尾怎么走

业务场景 → Harness 规划 → 小队建设 → 任务执行 → 结果度量和看护 → 自进化。

1业务场景SOP 裁剪确认，SR 是最小交付单元
2Harness 规划空间装配、环境匹配、上下文方案
3小队建设组 Agent Teams，按职责装载知识
4任务执行受管执行，断点转人工，重试有上限
5度量和看护留痕、分析、用量对账、监控
6自进化候选 → 立项 → 评测 → 发布 → 观察

各段做什么

阶段内容边界
① 业务场景拿确认过的场景 SOP 裁剪出本次流程；各系统按同一 SOP 拆任务、标步骤，平台据此分析步骤衔接和缺项。分析结果只是提示，不会自动拦你。必选步骤不能删；SR 只汇总进展，不另建验收。
② Harness 规划装配这次作业的"挽具"：空间圈定产品和版本范围、订阅要用的资产；按需求匹配池化运行环境和构建镜像；生成上下文选择方案——哪些候选、为什么排除、有什么冲突，都写明。范围外对象置灰；配置变化先看差异再确认。
③ 小队建设组 Agent Teams 分好工：做分析设计的拿现行规格和决策记录，写代码的拿批准目标和相关代码，做测试的拿验收场景和契约，协调的只拿目标、分工、结论和来源索引——不是把所有材料塞给每个人。角色只是分工，不产生新权限；全员沿用发起人的授权范围。
④ 任务执行AI、数字化作业和人工步骤在一个视图里推进。AI 卡住时保留现场、转成人工待办，人批一下、补点信息就能继续。临时故障有限重试，业务失败或拿不准就转人。代码生成 → 构建验证 → 失败反馈 → 修正，轮次有限。一个任务默认只有一个活跃执行；结果由人确认后才回写来源系统。
⑤ 度量与看护过程和知识消费全部留痕；按产品、空间、需求、资产版本、模型切着看使用、质量、耗时、消耗，能一路点到证据；三侧用量对账；来源同步和平台自身的健康有人看护。缺的和归因不了的单独列，不摊平、不凑均值。
⑥ 自进化线索和经验成候选，人工立项后做控制变量评测，审核通过才发布，上线后观察效果：达标关闭，退化回退。评测样本来自授权案例，脱敏、标注、人工入集、冻结版本。单次成功和模型自己的总结，不能直接变成共享规则。

06几条贯穿始终的原则

事实不搬家

业务事实归来源系统，平台维护关联、配置、执行和分析记录，对外操作以来源回执为准。两边不会各记一本账。

审批人不能是提交人

资产发布、标准发布、例外审批都要求审核人和提交人分离；所有操作落到发起用户头上，公共账号不能拿来放大权限。

变化不静默生效

父配置更新、上游资产更新、知识来源变化，一律先提示差异、等人确认。改进候选要立项，发布成功还要观察达标。没有"悄悄就变了"这回事。

知识按需取用

正文留在来源系统，任务执行时按需装配。准备装载和实际装载分开记，检索不等于用过，用过不等于验证过。
