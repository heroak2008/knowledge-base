SDD 工具链系统化方案

这份方案把十条一线反馈整理成一份可以排期、可以验收的工具链规划，由三条通道、六层架构（十三个组件）、一套度量和三期路线组成。基本思路是：规范由模型生成，对错由编译器、linter、测试这类确定性工具判定，人只在门禁失败时介入。

1总览：从痛点到体验

先说结果。下面左边是一线反馈里的现状，右边是方案落地后的样子；再往下一张表，每一行把一个痛点对到具体特性和技术方案，以及用户能感觉到的变化。

现在
  • spec-init 跑一夜没完，全流程一整天；小改动只能 vibe coding，文档形同虚设
  • 设计文档里有的字段代码里漏了；时序图只画主流程，异常场景缺失；基于 SPEC 开发还是遗漏
  • 生成后编译错误反复跑；圈复杂度高、风格和项目不一样
  • 跨仓隐性规则说不清，agent 理不透仓间关系；codewiki 颗粒度粗，Topic 识别不到
  • 0.5K 代码生成得散，一压缩上下文就丢；归档目录迁错
  • 人写文档、人审文档、人盯编译
之后
  • 小改动 30 分钟走完、0–1 次确认；默认通道 半天；spec-init 从小时级降到分钟级；所有改动都走流程
  • 每条需求挂测试；合并前自动报"有需求没实现、有实现没需求"，遗漏率 < 2%
  • 合并前编译错误 = 0，修复在 CI 里自动跑最多 3 轮；复杂度超标自动打回，风格锚定同模块范例
  • 改动方案直接列出波及哪些仓、哪些契约、哪些能力；定位命中率 ≥ 85%；踩过一次的规则变成 ADR / 契约测试
  • 压缩触发 = 0，一任务一上下文，进度随时可看；归档先看 diff 再确认
  • 人只在三个点做确认（范围 / 合并 / 门禁失败）；文档由模型生成、可随手重生成

怎么用研发人员在 CodeAgent CLI 里敲 /spec-init <变更描述>，后面按通道自动串起来，在三个决策点停下来等人（本地 CLI 或 CoreALM-Next 都行）。
怎么交付斜杠命令 + Skill 包（讲流程）+ MCP 服务（做判定），装进 CodeAgent 就能用；门禁在 CI 里跑，模型改不了。
怎么推进P0 两周先做不改引擎的改进 → P1 六周改引擎 → P2 八周补上下文与多仓 → P3 持续；看采用率和遗漏率，不看文档覆盖率。

支撑这些的是三条通道、六层架构和十三个组件：通道决定一次变更走多重的流程（第 5 节），架构和组件负责把每一步交给机器或确定性工具（第 4、6 节）。

3设计原则

七条原则，每条附落地含义，并对照今天的反面案例。

#原则落地含义反面案例（现状）
P1模型生成，确定性工具判定，人只在门禁失败时介入由 linter、编译、测试判定；模型产物不靠人逐行审人逐页审 spec markdown
P2范围优先：一切按"波及能力"做，不全仓分析、spec 生成、上下文都只覆盖波及集合spec-init 全仓扫描跑一夜
P3三层分离：描述层可抛弃、决策层 ADR、约束层契约/测试/steering人工修正不落在生成物上手改 wiki 后被重生成覆盖
P4可追溯：需求 ID → 场景 → 任务 → 测试 → 代码每条需求至少挂一个测试设计文档有、代码没有
P5一任务一上下文，状态外置协调者不写代码；进度写文件不靠记忆长会话压缩后迷失
P6仓库自描述验证清单、契约、规则都在仓内，agent 不靠口头交代脚本写死在流水线里
P7度量看采用率和遗漏率，不看文档覆盖率文档数量不作为考核项用文档数量考核

能力（capability）

一组可独立描述的业务能力，spec 的归档单位。

波及能力集合

一次变更可能影响的 capability 集合，所有分析和生成的范围边界。

Topic

按业务能力组织的代码区域索引，是"定位到符号"的入口。

通道

一条端到端作业链路模板：轻 / 标准 / 重。

门禁

确定性工具的通过 / 不通过判定，模型不能修改门禁。

决策收件箱

所有人工介入点的统一形态：决策包 + 证据 + 推荐 + 反方证据。

4目标架构

4.3 交付形态：斜杠命令 + Skill 包 + MCP 服务

十三个组件不是一套独立的 SDD CLI。研发人员在 CodeAgent CLI 里敲一条斜杠命令（例如 /spec-init 订单服务增加幂等重试）触发，命令背后是一组 Skill 加一组 MCP 服务，装进任何支持自定义命令、Skill 和 MCP 的 CodeAgent 就能用。后续会引导大家优先从 CoreALM-Next 进入，本地用 CodeAgent CLI 单独跑作为试点入口和长期兜底。

  • 斜杠命令（入口层）：每个 Skill 对应一条命令，放在 CodeAgent 的自定义命令目录（如 .claude/commands/、.codex/prompts/），正文指向该 Skill。/spec-init <变更描述> 是主入口，一条命令完成分级、提案、spec 起草并串起后续步骤；/sdd-verify、/sdd-archive 等可单独重跑某一步。
  • Skill 包（sdd-skills，prompt 层）：每个组件对应一个 SKILL.md 加参考资料和可选脚本，讲流程、模板、检查清单，告诉 agent 何时调用哪个工具。Skill 里不写判定逻辑。
  • MCP 服务（sdd-mcp，确定性层）：分级规则、指纹哈希、追溯解析、归档脚本、事件落盘都做成 MCP 工具（sdd_triage、sdd_spec_init、sdd_context、sdd_check_trace、sdd_gate、sdd_archive 等）。工具返回统一 status：ok / decision_required / gate_failed，decision_required 携带 §5.1 的决策包。
  • 门禁在 CI 执行：sdd_gate 只触发 CI 按 verify.yaml 跑 build / test / lint，sdd_gate_result 读回结果。判定不放在模型能改写的地方。
  • 工件与事件：spec、trace、ADR 等工件在仓库内；事件由 sdd-mcp 落盘为 JSONL，给度量（C13）和平台（方案 B）消费。

与 CoreALM-Next 的接入方式见 方案 B：平台通过 M5 资产登记、M17 镜像预装、M18 基线冻结、M4 断点转决策包接入，不新增模块。

分级结果可以被人覆盖，但必须选择原因，覆盖记录用来调整判据。轻通道不是绕过 SDD：它把流程压缩到一页提案加可执行验收，目的是让小改动也愿意走 SDD，而不是直接 vibe coding。

5.1 人工确认的形态：一页决策卡

范围确认时，人看到的是一张决策卡，而不是逐页的 markdown。卡片列出变更是什么、走哪条通道、判据明细、波及哪些能力、spec 覆盖情况和可执行验收标准；下面是模型推荐与置信度、必须呈现的反方证据，以及四个操作（批准、否决且理由必填、补充信息、亲自看）。做推荐的是模型，做决定的是人；否决和复核都留痕。

这与 CoreALM-Next 的决策收件箱是同一种形态。SDD 工具链的三个人工点都复用它，不另建审批流。

L3 执行层 · 一任务一上下文

C7 执行编排 P0

D 执行验证 解决 #7 · 判定：结构约束
  • 协调者只读不写（不持有编辑工具）；子代理一任务一新鲜上下文，只回传摘要（做了什么、改了哪些文件、遗留）。
  • 状态外置：tasks 勾选、progress.md、decisions.md；每次尝试一份续作记录。
  • 任务粒度上限 初值 ≤ 300 行或 ≤ 5 文件，超限拆分；实现任务内禁止触发上下文压缩，超限即拆。
  • 探索（读代码、找位置）交子代理，不占实现会话。

验收：实现任务压缩触发次数 = 0；长任务一次完成率提升；重复编辑 / 回退次数下降。

L4 验证层 · 确定性判定

C8 确定性质量门禁 P0

C 追溯 解决 #10 · 判定：确定性工具
  • 项目：圈 / 认知复杂度、函数与文件长度、格式化、lint、命名、import、安全扫描；阈值版本化。
  • 时机：进行中——子代理标记任务完成前必须本地跑门禁；CI 再跑一次。
  • 风格锚点：同模块 2–3 个范例文件注入上下文，让模型模仿而不是靠规则解释。
  • steering / constitution 只负责解释"为什么"，判定交给 linter。

验收：一次门禁通过率；复杂度超标数；与项目风格的 diff 量下降。

C9 合规检查 agent P1 shadow → P2 阻断

C 追溯 解决 #2 #9 #6 · 判定：独立模型 + 证据
  • 独立上下文（不是写代码的会话）、只读凭据。输入：diff + REQ 列表 + 场景 + trace。输出：逐条 Pass / Fail / Partial + 证据（文件:行）。
  • Fail 回执行层修复，循环上限 3 轮，超限转决策收件箱。
  • 先 shadow（只报告不阻断）跑 2–4 周，统计漏报 / 误报，再转阻断；证据不足的条目降为提示项。

验收：漏报率（人工复核对照）；误报率；每变更检查时长。

C10 验证清单与 CI 自愈 P0 清单 → P1 自愈

  • 编译前置：实现过程中逐文件编译 / 类型检查，错误当场修。
  • CI 失败 → 自愈 agent（只拿失败日志 + 相关 diff）→ 推修复提交 → 上限轮次 → 转人工。
  • 现有 e2e demo 脚本改为读 verify.yaml，不再写死。
  • 凭据分离：门禁脚本和测试期望放在 agent 写不到的路径；测试期望先在参考实现上验证。

验收：合并前编译错误 = 0；自愈成功率；人工介入次数 / 变更下降。

8度量体系

首要指标是 SDD 通道采用率，它直接反映流程过重的问题有没有缓解。质量看遗漏率，文档只看生成物被人工修改的次数。

十七个指标，分六类；每期结束复盘一次判据与阈值
首要指标
  • SDD 通道采用率走 SDD 通道的变更 / 全部变更 ↑
效率
  • 通道端到端时长各通道 P50 / P90 轻 ≤ 30 分钟，标准 ≤ 半天
  • spec-init 时长P50 ≤ 10 分钟
  • 人工介入次数 / 变更该变更的决策包数 轻 ≤ 1，标准 ≤ 2
  • 人工撰写字数 / 变更人写的文档字符数 趋近 0（只确认不撰写）
质量
  • 一次通过率首次门禁 + 合规检查通过的变更占比 ↑
  • 遗漏率合规检查 Fail 条目 / 需求条目 < 2%
  • 编译修复循环次数每变更编译失败 → 修复轮次 ↓
  • 复杂度超标数门禁报告的超阈值函数数 ↓
  • 归档修正次数人工修正归档结果的次数 → 0
上下文
  • 实现任务压缩触发次数实现类子代理触发压缩的次数 = 0
  • 地图命中率固定问答集 top-5 定位正确率 ≥ 85%
  • 上下文 token 占用实际装载 / 预算 不超预算
自治
  • 自愈成功率CI 失败由自愈 agent 修复的占比 ↑
  • 合规检查漏报率 / 误报率人工复核对照 漏报 ↓，误报可接受
文档
  • 生成物手改次数描述层文件的人工提交数 = 0
  • spec 自动生成占比agent 起草的 spec / 全部 spec ↑（不看覆盖率）

P0 Phase 0 快速改进（第 1–2 周），不改引擎架构

  • verify.yaml 规范 + 编译前置 + 修复轮次上限（#5）
  • 一任务一上下文 + 状态外置（#7）
  • linter / 复杂度门禁进"完成前检查" + 范例文件锚点（#10）
  • 需求模板三栏 + 必答清单（#6）；归档 dry-run + validate（#8）；指标基线采集

验收：1 个试点产品跑 ≥ 10 个变更；合并前编译错误 = 0；实现任务压缩触发 = 0；建立一次通过率、时长、人工介入次数基线。

P1 Phase 1 引擎改造（第 3–8 周）

  • 分级器 + 轻 / 标准通道（#1）
  • 增量 spec-init + 指纹缓存（#1）
  • 需求 ID + trace + schema-first 生成（#2 #9）
  • 合规检查 agent shadow 模式（#2 #9）；CI 自愈 agent（#5）；ADR 门槛 + 补录时限

验收：轻通道 P50 ≤ 30 分钟；采用率 ≥ 60%；遗漏率 < 5%；合规检查漏报 / 误报基线完成。

P2 Phase 2 上下文与多仓（第 9–16 周）

  • 符号地图（主语言适配器）+ Topic 索引（#4）
  • 契约仓 + 协调仓 + workspace 组装器（#3）
  • 漂移检测 + 所有权标记 + steering 回灌；度量看板；合规检查转阻断

验收：地图命中率 ≥ 85%；跨仓变更一次通过率提升；生成物手改 = 0；遗漏率 < 2%。

P3 Phase 3 持续（16 周后）

  • 保真度测试（参考实现 = 现有生产系统）用于核心服务
  • 自动化分级扩大低风险自动通过
  • 更多语言适配器；隐性规则事件持续转 ADR / 契约测试；evals 数据集随变更积累

10风险与对策

风险对策
产业用户抵触"又是文档"轻通道 + 只确认不撰写；不考核文档覆盖率；提案压到一页；人工介入点固定为三个
门禁慢拖垮吞吐增量编译、并行、缓存；门禁时长纳入指标；门禁速度优先于门禁数量
合规检查误报导致不信任shadow 先行；每条 Fail 带证据；证据不足降为提示项
契约仓变成新治理负担只对波及接口强制；schema-first 从代码生成契约优先
agent 改测试 / 门禁作弊凭据分离；测试期望在参考实现上验证；门禁在 agent 写不到的路径（见第 11 节 METR / ImpossibleBench 证据）
符号地图语言覆盖不足先主语言；未覆盖语言降级为 codewiki + 文本检索
与 CoreALM-Next 边界争议已确认：SDD 工具链独立建设、独立运行；平台只通过 M7 连接器调用，用试点数据再定内化（见方案 B）
长任务仍然散粒度上限 + 禁止压缩 + 强制拆分 + 状态外置
模型差异导致效果波动evals 数据集随变更积累；模型路由与版本记入执行基线
