# CoreALM-Next 介绍说明

> 依据《CoreALM-Next系统设计方案 v1.18》《研发作业知识工程实施方案 v1.0》《SkillOpt融合分析》整理。本文为介绍性材料，具体规则以设计基线为准。

## 0. 一句话定位

CoreALM-Next 是产业装备部面向研发场景的 **AI 原生作业平台**：连接既有作业系统（CoreALM、DTS、CIDA、珊瑚、CloudPipeline 等）、Agent Teams、公司 MaaS 和池化资源，提供**任务协同、资产复用、执行记录、用量分析及持续改进**能力，把研发人员的作业活动统一到一条规范化、可度量、可扩展、可进化的闭环流程上。

平台共 18 个逻辑模块（M1–M18），按"管理对象 + 维护状态 + 作出决定"划分，同一事实只有一个写入模块，其他模块通过接口和回执使用。

## 1. 工作空间按什么维度建立（M1 作业空间）

**核心维度：来源对象（产品/服务/版本）+ 单父级空间树 + 订阅配置。**

- **按业务范围组织，不按用户团队拆分**：一个空间可关联多个来源产品/服务/版本对象（均从 M7 同步目录中选择建立，不允许手填地址），同一来源对象可被多个空间复用，天然支持跨产品、跨服务作业。
- **单父级树形结构**：子空间对父配置可**继承 / 覆盖 / 忽略**；父配置更新**不自动覆盖**子空间，只提示差异，子空间管理者逐项确认后采用，可保留本地覆盖。
- **关联受控**：成员可提议关联来源对象，空间管理者确认后生效；项目对象仅作视图聚合键，不参与执行装配。
- **跨空间资产复用走订阅**：知识订阅不授予来源读取或装载权限（权限始终归 M9/iRight 校验）。
- **生命周期简化**：只有"使用中 / 已归档"两态；归档保留关联与历史，恢复须特殊申请审批；存在未终结执行时阻止归档。迁移支持预览差异、保留空间身份、禁止成环。

**规范化体现**：空间是范围与配置的**唯一生效边界**——任务（M2）、知识装配（M5）、执行（M4）都在空间划定的来源范围内工作，变化一律"先看差异再采用"。

## 2. 小队 / Skill 等 AI 资产的版本管理与更新同步（M5 资产管理 + M18 执行基线）

### 2.1 统一资产模型

M5 统一管理 **Agent 配置、Skill、Workflow、场景 SOP、上下文模板、装配策略、构建验证配置**，按类型定义内容结构。资产由产业用户维护；网关策略是平台专属资产，不向产业管理员开放。

### 2.2 版本管理生命周期：草稿 → 试用/评测 → 独立审核 → 不可变发布

- **草稿与发布分离**：发布版本不可修改；草稿可在授权范围试用。
- **证据门槛**：正式发布必须提交对应版本的**试用或评测证据**，由**不同于提交人**的审核者批准（审核分离由 M9 强制）。
- **派生定制**：支持派生并保留上游版本及差异；上游更新只提示差异，维护者决定是否合入，合入形成新草稿重新审核，**不自动覆盖定制**。
- **资产包**：可锁定组成版本，独立评测、审核、发布；组成版本归档时提示修订而非自动归档整包。
- **归档**：支持单版本和整体归档，归档后禁止新订阅/派生/新执行采用；在途执行默认继续原版本。

### 2.3 更新同步：差异确认 + 源变化传播

- 空间采用资产的新版本仍走 M1 的"差异预览 → 确认发布"，不静默升级。
- 知识类来源（代码仓 SPEC、文档平台、云见经验）由 M7 观察修订/删除/撤权事件 → M5 将受影响索引/摘要标记待更新或不可用 → M9 限制后续未授权读取 → 在途执行保留原条件，需要改变时显式派生新基线。
- 普通知识沿用源正文和原生修订（Git 修订、文档版本、评审回执即依据）；只有需发布复用的 Skill/SOP/策略才走完整 AssetRelease 生命周期。

### 2.4 执行侧的可还原性（M18 执行基线）

每次执行冻结 **ContextManifest**：选定知识修订、装配策略版本、实际装载确认和局部变化，区分"准备装载"与"实际装载"，保证历史执行可还原、可追溯，不靠事后查看当前文件推断历史。

### 2.5 如何做到规范化 / 可度量 / 可扩展 / 可进化

| 目标 | 机制 |
| --- | --- |
| **规范化** | 统一 Task 关联规则与人工审核（M2）；场景 SOP 模板化、必选步骤不可删（M3）；资产发布流程统一裁决面（M6 三类裁决队列：资产发布/知识固化/改进发布与回退） |
| **可度量** | 全过程留痕：执行记录（M11）+ 用量三侧去重统计（M14）+ 运营分析多维下钻（M8）；指标口径版本化，缺失和未归因单列 |
| **可扩展** | 空间单父树 + 订阅复用；资产派生与组合；builtin 接入逐系统登记扩展（M7）；模块按对象划分，新能力挂接而非重构 |
| **可进化** | 候选经验 → 人工立项 → 评测验证 → 审核发布 → 上线观察 → 回退/继续（M13）；配合 M12 评测实验、M16 冻结数据集，SkillOpt 类自动训练循环作为治理流水线的执行引擎接入 |

## 3. 端到端作业流程：业务场景 → Harness 规划 → 小队建设 → 任务执行 → 结果度量与看护 → 自进化

```
业务场景 → Harness规划 → 小队建设 → 任务执行 → 结果度量与看护 → 自进化
   │            │            │            │             │              │
 场景SOP     空间装配+     Agent Teams   M4受管执行    M8/M11/M14     M12/M13/M16
 裁剪确认    运行环境M17   资产订阅M5    +M18基线     +M15监控        候选→验证→发布
```

**① 业务场景**：以少数跨作业领域的场景 SOP 为依据（M3），IPD 提供总体阶段约束；产业用户裁剪可选步骤、必选步骤不可删，确认后形成本次作业的流程基线。SR 作为最小可验证交付单元，各系统按同一 SOP 拆分并标记步骤。

**② Harness 规划（作业装配）**：在 M1 完成"空间装配"——选定产品/版本范围、订阅资产与知识来源、确认配置差异；M17 按需求分析和兼容匹配分配池化运行环境与构建镜像；M5 生成上下文选择方案（ContextSelectionPlan），明确候选、排除理由与冲突。

**③ 小队建设（Agent Teams 装配）**：为任务组建 Agent Teams，按职责最小装载知识：分析/设计角色优先现行 SPEC 与有效 ADR，编码角色优先批准目标与相关代码，测试角色优先验收场景与契约，协调 Agent 只共享目标、分工、结论和来源索引（KE 实施方案 §7）。角色是执行分工而非新授权主体，所有成员沿用发起用户权限范围。

**④ 任务执行**：M4 以 Agent Teams 推进，统一呈现 AI、数字化作业和人工步骤；AI 断点保留现场转人工待办（决策收件箱模式），临时故障有限重试、超限转人工；代码生成→构建验证→失败反馈→Agent 修正→再次验证限定轮次。同一 Task 默认只有一个活跃执行。执行结束后由用户确认结果，M2/M7 以用户身份更新来源 Task 并以回执确认。

**⑤ 结果度量与看护**：M11 追加保存实际过程与知识消费回执；M8 按产品/服务/空间/SR/资产版本/模型多维比较使用、质量、耗时与消耗，支持下钻到证据；M14 三侧 Token/Credit 去重核对；M15 看护平台与来源同步健康；M6 质量管理区分自动检查事实与人工审核决定，必选项未通过阻止结果确认。

**⑥ 自进化**：分析线索和任务中提炼的经验先成为**候选**（不自动生效）→ 人工立项（M13）→ M12 控制变量评测（固定任务/模型/环境/标准，A/B/C/D 分步实验）→ M6 审核、M5 不可变发布 → 上线观察，达标才关闭，退化则回退。M16 把授权案例加工成脱敏标注、人工入集、冻结版本的评测数据集，独立验证集滚动更新，防止过拟合。由此形成"执行产生证据 → 证据驱动评测 → 评测驱动资产升级 → 更好的资产服务下一次执行"的自进化闭环。

## 4. 关键设计原则（贯穿全流程）

1. **事实来源分离**：业务事实归来源系统，平台只维护关联、配置、执行、分析和审核记录，所有对外动作保留来源回执。
2. **审核分离与全程追溯**：资产发布、标准发布、例外审批人与提交人必须不同；一切操作追溯到发起用户，公共账号不扩大权限。
3. **不静默、不自动**：父配置更新、上游资产更新、知识变化一律差异确认；改进候选一律人工立项；发布成功不等于改进成功。
4. **知识按需消费**：正文分布维护在来源，任务按需装配；候选、准备装载、实际装载和效果分别留痕，任一阶段不代替下一阶段。
