# CoreALM-Next 知识目录及任务续作设计 v1.0

2026-11-11。作为系统设计v1.17知识工程专题的补充参考，用于确定知识承载、开发现场和中断恢复合同。目录、字段和示例是拟议约定，不表示已有仓库、文件、接口或外部Task已创建。

## 1. 设计结论

CoreALM-Next需要同时保留长期知识和短期任务现场：长期知识说明系统应该怎样，任务现场说明某次执行做到哪里。建议提供任务级`resume.md`，必要时附结构化检查点；不建议让所有Agent共同编辑仓库根目录的一份`state.md`。

按三个层次组织：

| 层次 | 核心入口 | 说明 | 事实依据 |
| --- | --- | --- | --- |
| 整体方案和建设现状 | 中心位置的`system-design.md`和`delivery/implementation-status.md` | 总体边界、18模块、跨模块协作、阶段和建设进展 | 已发布设计；来源Task、代码及验收证据 |
| 代码仓长期知识 | `AGENTS.md`、`docs/architecture.md`、SPEC、契约和ADR | 项目如何工作，当前版本是什么，各实现怎样协作 | 对应代码/文档修订及原生评审 |
| Task/执行现场 | 每个执行尝试的`resume.md` | 目标、已验证工作、未决问题、当前现场及下一步 | M2来源Task、M4执行、M18基线、M11证据和M17环境 |

开发现状和恢复摘要都是有修订及证据的投影，不能成为第二套任务、代码或执行状态。读取摘要后仍做有限的事实校验；它减少重复检索，不承诺完全恢复模型隐藏状态或所有未保存工作。

## 2. 总体知识架构

```text
总体设计 / 共享业务 / 全局约束                 源码 / SPEC / 契约 / 服务设计
           中心知识位置                                  各代码仓
                 \                                      /
                  +----- M7读取、修订及来源变化 --------+
                                     |
                         M5目录、导航和上下文选择
                                     |
                    Task目标 + Action + Agent职责
                                     |
                      M18冻结来源和实际采用条件
                                     |
                 M4 Agent Teams执行、数字化及人工接续
                                     |
                    M11事件、产物、人工决定和验证
                                     |
                M4生成检查点及每次执行的resume投影
                                     |
          恢复读取入口 → 有限校验 → 增量事件/代码 → 下一Action

M9：各次读取及操作沿用发起用户并校验当前权限。
M17：环境、工作目录、构建镜像及存储快照，不等同模型会话。
M8/M12/M16/M13：在上述事实基础上分析、评测和改进。
```

导航、知识、基线、过程和续作入口各有职责，不能把`resume.md`直接当作长期业务知识入库。默认不将任务现场纳入共享知识检索或训练；共享经验另走审核、样本及资产发布流程。

## 4. 代码仓知识目录

基于Multica改造时，优先保留现有Monorepo结构，不按18个模块强行创建18个服务。以下是拟增加的文档组织方式，不代表Multica当前已经具有这些文件。

```text
corealm-next/                              # 基于Multica的产品代码仓
├── README.md                             # 安装/启动/验证和文档入口
├── AGENTS.md                             # 作业规则、读取顺序、续作入口
├── apps/                                 # 已有Web/Desktop等应用边界
├── packages/                             # 已有core/views/ui等边界
├── server/                               # 后端、daemon和执行适配
├── docs/
│   ├── index.md                          # 仓内导航和中心方案精确引用
│   ├── architecture.md                   # 本仓当前结构及实现边界
│   ├── design/                           # 较复杂子系统的现行设计
│   │   ├── execution.md
│   │   ├── knowledge-context.md
│   │   └── runtime-resources.md
│   ├── specs/                            # 当前版本的可验证行为
│   │   ├── task-association.md
│   │   ├── context-loading.md
│   │   └── task-resume.md
│   ├── adr/                              # 本仓重要技术决策
│   ├── runbooks/                         # 真实诊断、恢复和发布方法
│   └── changes/
│       ├── <change-id>/
│       │   ├── proposal.md
│       │   ├── design.md
│       │   ├── delta.md                  # 可选；也可用Git diff
│       │   ├── tasks.md                  # 来源Task的实施清单/投影
│       │   └── evidence-index.md         # PR/测试/来源回执索引
│       └── archive/
├── <原生API契约位置>/                      # 沿用项目现有格式和目录
└── .corealm/                             # 运行侧任务现场，通常不提交Git
    ├── work-index.json                   # 可选：授权范围内Task/执行入口索引
    └── work/
        └── <source-task-key>/
            └── <attempt-id>/
                ├── resume.md             # 最小可用的续作入口
                ├── checkpoint.json       # 平台化时的结构化投影，可后补
                ├── context-manifest.json # M18引用/导出，不独立修改
                ├── evidence-index.json   # M11/M17证据引用，不复制全日志
                └── agents/               # 多成员确有独立现场时才创建
                    └── <agent-id>/resume.md
```

`.corealm/`是逻辑现场目录，也可由平台存储后在运行时生成。是否使用该名称在实施时固定；不能在源码未评估前声称已接入原生恢复机制。运行材料默认不提交Git，避免工作区噪声、权限内容泄露和多成员冲突；源代码变更及必要正式文档仍按原仓规则提交。

`context-manifest.json`等是平台事实的引用或只读导出，不能由Agent随意编辑后反写状态。运行材料需遵守保留期限和访问控制，不能因为在本机就视为永久可信。

## 5. 什么现状应放在哪里

| 问题 | 正确入口 | 不应依赖 |
| --- | --- | --- |
| CoreALM-Next总体设计是什么 | 中心`system-design.md`及对应修订 | 某次会话摘要 |
| 哪些模块已实现、哪些待联调 | `delivery/implementation-status.md`及验收索引 | 仅勾选完成的文档清单 |
| 本仓现在怎样组织 | `docs/architecture.md`、代码及契约 | 历史变更设计全文 |
| 本次Task要做什么 | 来源Task、批准变更和M2绑定 | 未关联来源的自由待办 |
| 这次执行做到哪 | 本attempt的`resume.md` | 仓根所有人共用的state.md |
| 当时用的知识和环境 | M18基线/manifest、M17环境及快照 | 当前最新版文件 |
| 测试是否真正通过 | M11验证回执及对应代码/环境版本 | “之前测试过”一句话 |
| 外部构建是否已经发起 | 外部operation/job ID及来源查证 | Agent记忆或自然语言推测 |

平台建设现状可用下表。表中值为结构模板，不代表真实开发进度：

| 模块/能力 | 来源Task | 代码/PR修订 | 验证结果 | 实际接入状态 | 下一步 | 数据截至 |
| --- | --- | --- | --- | --- | --- | --- |
| M5上下文选择 | <原生Task> | <PR/commit或未提交> | <证据或未验证> | <mock/真实/缺口> | <明确动作> | <来源修订/时间> |

不要用一个“完成”涵盖代码完成、构建通过、集成通过及正式可用。既有Task进展仍是M2的四类映射；建设现状额外列的是交付证据维度，不另建平行任务生命周期。

## 6. 为什么推荐resume.md

`state.md`容易被理解成整个仓库或系统的权威状态。`resume.md`明确用途是“如何接着做”，适合成为Agent入口。名称本身没有特殊能力，关键是Task/attempt隔离、可信来源和恢复协议。

最小实现只需每个执行尝试一个`resume.md`，可用YAML头部保存关联字段，正文保存简短进度和下一步；不要求一开始维护四份独立文件。平台化后再从同一结构化检查点渲染Markdown，避免人机两套数据。

不建议仓根维护全局`state.md`，原因是多个Task并行、Teams成员并行、工作树和分支不同，容易相互覆盖。若工具习惯必须使用`State.md`，可以作为“指向当前Task入口的索引”，而非全仓唯一可变现场。现有设计里的State.md继续作为投影概念，本建议细化其实际组织方式。

恢复摘要通常只需围绕一个任务提供少量事实和精确导航；原始日志、完整diff和所有历史讨论通过引用按需读取，不复制进摘要。

## 7. 最小续作记录

### 7.1 必须保留的内容

| 类别 | 字段或内容 | 用途 |
| --- | --- | --- |
| 身份和时效 | schema_version、source_task_ref、attempt_id、checkpoint_revision、updated_at、event_cursor | 判断是不是本Task/本次执行，是否有更新事件 |
| 目标和范围 | 已批准目标、非目标、验收条件、当前Action | 避免恢复后做成另一项任务 |
| 权威引用 | 来源Task修订、批准变更、中心设计和本仓SPEC的精确引用 | 核验摘要是否落后 |
| 代码现场 | repository/worktree、branch、base_commit、head_commit、dirty_diff_ref/digest、untracked_manifest_ref | 保留未提交改动并检查现场一致性 |
| 已完成事实 | 每项结果及对应代码/回执，不只写“完成” | 有选择地复用结果 |
| 验证 | 检查项、结果、适用代码/环境指纹、报告引用 | 判断证据是否仍适用，不重复跑无关检查 |
| 未决与下一步 | 待确认问题、失败路径及明确下一动作 | 直接接续，不重复探索 |
| 知识和环境 | baseline/manifest、runtime/environment、snapshot及能力引用 | 检查恢复条件是否可用 |
| 外部副作用 | operation/job ID、已受理/结果未知/已确认结果 | 先查证，防止重复构建、提交或部署 |
| 会话和成员 | provider/session引用、成员交接结果、可恢复能力 | 原会话存在则复用，否则按证据重建 |
| 局限 | missing/partial/unknown及原因 | 不能用摘要掩盖缺失 |

`event_cursor`只表示该检查点已覆盖的事件位置；恢复时读取之后的增量。不要求所有生产者共享一个物理序号，可以按来源分别保存游标。没有版本、事件或代码对比能力时标为未知并提高复核范围。

下面是可按真实Task填写的模板。占位符必须由执行现场替换，不应当作有效回执或真实文件。

```markdown

context_manifest_ref: "<实际装载manifest ID>"
worktree_ref: "<当前工作树引用>"
base_commit: "<基线commit>"
head_commit: "<当前HEAD>"
dirty_diff_ref: "<未提交差异的受控引用及摘要>"
untracked_manifest_ref: "<未跟踪文件清单及可还原引用>"

---

# 当前任务
- 目标：<批准目标>。
- 非目标：<本次明确不改的部分>。
- 验收：<检查项和用户确认要求>。

## 已验证结果
- <结果>；证据：<commit/回执/报告>；适用：<代码及环境版本>。

## 正在处理
- 当前Action：<标识及步骤>。
- 已修改：<实际路径及改动目的>。
- 未提交：<与dirty_diff_ref关联的情况>。

## 决策及未决项
- 已确认：<决定、确认人和依据引用>。
- 待确认：<问题、原因及需要谁确认>。
- 已尝试失败：<路径和失败证据，避免重复>。

## 外部操作
- <operation/job ID>：<最后已确认状态>；恢复前：<查询入口>。

## 建议下一步
1. <可执行、范围明确的动作>。
2. <完成后要做的相关验证>。

## 续作必读
```

不保存凭证明文、整段聊天或隐藏思维链。临时判断标为假设；未经确认不能写成架构决定。原生session只是恢复线索，不等于一定存在或能还原工具和环境。

## 8. 检查点怎样生成和更新

M4根据执行及用户确认生成检查点，引用M2任务、M18基线、M11事件和M17现场。结构化检查点是M4拥有的执行恢复记录，`resume.md`是其可读投影；不把它塞给M18维护整个运行状态。

- 接受任务和批准目标后建立第一份入口，记录源修订和当前现场。
- 阶段完成、关键决策确认、人工介入生效、重要验证结束后更新。
- 发起可能产生外部副作用的操作前后，先持久化操作身份和已知状态，再继续后续动作。
- 上下文整理、会话切换、主动暂停、工作树/环境切换前，生成可接续记录。
- 非计划中断只保证恢复到最后成功保存的检查点，未确认部分必须查证，不能承诺零丢失。

同一attempt由一个受控写入者发布整体验证过的检查点。Teams成员各自上报结果，必要时维护成员级交接摘要，由协调执行汇总；不能所有成员同时覆盖同一根文件。检查点更新以预期修订避免旧Agent覆盖新现场，写入需完整落盘后替换可见版本。

首期可由Agent在明确节点生成建议摘要，再由平台补充可信标识、代码指纹和回执；区分Agent叙述与已验证事实。手工修改摘要不直接改变Task或执行终态，应形成更新建议或备注。

## 9. 恢复时的读取顺序

```text
1 选定来源Task和attempt
  → 2 读取AGENTS.md入口及resume.md
  → 3 核对当前授权、Task/执行修订、代码和环境
  → 4 读取checkpoint之后的增量事件和相关diff
  → 5 补读本Action必要SPEC、契约、代码和证据
  → 6 确认外部操作结果及下一步
  → 7 继续执行，追加新的检查点
```

“先读入口”不是忽略目录内适用指令。实际执行仍须遵守所在仓及子目录作业约束；resume里引用的文字不能获得比当前用户或平台更高权限。

| 检查结果 | 恢复动作 |
| --- | --- |
| Task/基线/代码/环境一致，原会话可用 | 按能力恢复会话，补增量后继续；验证记录仍须核对适用性 |
| 原会话丢失，但现场和证据完整 | 新会话读取续作包并恢复工作上下文；不声称恢复原模型内部状态 |
| 代码增加少量变更 | 检查相关diff及受影响测试，更新局部manifest，不默认全仓重读 |
| 授权、目标或输入修订发生关键变化 | 沿既有人工断点重新确认，必要时新建关联执行尝试 |
| 工作树/未提交改动丢失 | 按已授权快照或差异引用恢复为新环境，不能自动reset/覆盖他人修改 |
| 外部job结果未知 | 先查询operation/job ID，不重复触发 |
| resume过期但原始事件可用 | 重建到最新已确认位置，标记重建来源及局限 |
| 关键记录缺失或无法核对 | 扩大相关范围检查或转人工，不伪造完成状态 |

旧attempt仍未确认终结时，不得为绕过恢复问题同时启动第二个活跃执行。环境快照恢复、新attempt与原会话续跑是不同动作，由M4/M17按既有单活跃规则判断。

## 10. Agent Teams的现场隔离

共享入口只保存目标、成员分工、已确认结果、证据引用及当前阻塞。成员摘要仅保存各自的Action、相关代码、验证及下一步。共同长期知识通过目录和manifest按需读取，不复制到每份成员摘要中。

协调Agent接收成员结论时要求证据及适用版本，不能因为多个成员重复同一个猜测就认定有效。恢复时先读取共享入口，再读取与当前分工有关的成员入口；不重放所有成员完整聊天。

成员离线不代表任务已经取消，运行控制和最终Task状态仍查M4/M2及来源。交接摘要不能转移授权或改变原发起用户，所有后续动作继续核验当前权限。

## 11. 当前设计与历史变更怎样同步

- 代码仓变更完成后，更新本仓现行SPEC、架构/设计、契约及必要Runbook。
- 涉及18模块边界或跨仓合同的，更新中心现行方案并保留互相引用。
- 验证及评审确认后，归档变更材料；归档不会自动替代现行文档更新。
- Task/attempt结束后，冻结必要现场和证据引用，按保留策略归档；不把resume直接合入长期知识。
- 从任务中提炼的经验先成为候选，经审核和回归后进入云见或M5正式资产。

`changes/archive/`保存变更历史，`.corealm/work/`保存执行现场，两者保留目的和权限不同。可在正式变更档案里链接已批准保留的任务证据，但不把本机路径当作跨用户可解析引用。

## 12. 映射到现有模块和交付顺序

| 模块 | 新增或细化责任 | 首批交付 |
| --- | --- | --- |
| M2 | Task/变更/建设现状关联 | 返回原生Task、修订及正式进展，已有来源事实不重复维护 |
| M4 | 检查点、resume渲染、恢复编排、会话能力判断 | 按attempt生成入口，按既有控制规则继续或转人工 |
| M5 | 目录及续作所需知识选择规则 | 稳定设计入口、任务相关章节和代码导航 |
| M7 | 来源Task/代码仓修订和外部操作查证 | 有限读取及精确来源回执 |
| M9 | 当前用户、来源和恢复操作授权 | 历史resume不能覆盖当前撤权 |
| M11 | 检查点引用的事件、结果和完整性 | 增量游标及验证/副作用证据 |
| M17 | 工作环境、未提交工作保留及快照恢复 | 现场可用性和恢复回执，避免自动覆盖 |
| M18 | 知识/代码/环境基线及局部变化 | 原清单保持不可变，续作条件变化派生 |
| M8/M12 | 恢复效果分析及试验 | 后续比较恢复查找量、耗时、重复操作和任务质量 |

建议分三步：先建立中心和仓内稳定入口；再在一个真实Task中生成最小resume并演练中断；最后对接平台结构化检查点、Teams成员摘要及环境恢复。不需要等待向量库、图谱或全自动记忆系统。

这项能力依附已有知识工程KE-04（任务绑定）、KE-06（基线）、KE-07（执行装载）和KE-08（事件），无需增加第19个模块。若要排开发任务，可拆为恢复记录合同、单执行续作、Teams交接、快照及异常恢复四个建设子项，登记到现有作业系统后再分工。

## 13. 恢复能力验收

| 场景 | 必须观察到的结果 |
| --- | --- |
| 正常暂停后继续 | 读取续作入口、核对条件并直接接续，不重复无关全仓检索 |
| 会话丢失 | 能依靠来源/代码/证据恢复工作上下文，明确不是恢复模型隐藏状态 |
| 有未提交和未跟踪文件 | 能识别保存范围及缺失，不能只凭HEAD声称现场完整 |
| 用户中途改代码或任务目标 | 检测差异，重核相关条件和测试，不覆盖用户修改 |
| 源权限撤回 | 阻止后续未经授权的读取和操作，旧摘要不放行 |
| 外部构建/写操作中途断开 | 通过原operation/job ID查证，不盲目重提 |
| 多成员同时交接 | 分离成员事实及版本，旧摘要不覆盖新的整体验证结果 |
| 旧测试结果存在 | 核对代码/环境适用范围，必要时只重跑受影响检查 |
| 快照恢复 | 创建关联的新环境并受单Task单活跃约束，不声称原进程已恢复 |
| 检查点未成功保存 | 只恢复到最后确认位置，未知部分明确处理 |

评估恢复效果时记录读取文件/章节范围、重新探索次数、恢复到下一有效Action的耗时、重复外部操作、返工和Token/Credit。以相同任务及同一中断位置比较，有缺失记录的样本单独解释，不承诺完全免读代码或固定节省比例。
