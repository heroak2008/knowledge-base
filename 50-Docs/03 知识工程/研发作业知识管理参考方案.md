# 基本信息

> 日期：2026-11-11｜版本：v1.0｜性质：讨论汇总与实施参考，非已批准的团队制度
>
> 适用范围：以一个最小 `order-service`（下单与扣库存）为例，逐步扩展到多服务、人机协同研发。
>
> 本文统一此前讨论，并修正其中过于绝对的建议。OpenSpec / Spec Kit 仅作为实践参考；是否引入工具、delta 或 archive 目录，尚未作出实施决定。本文不修改现有项目。


> 平台实施承接：[AI原生研发作业知识工程实施方案](AI原生研发作业知识工程实施方案.md)。已纳入CoreALM-Next系统设计v1.17，包含模块职责、数据合同、KE建设任务及KA验收；本参考方案继续保留内容维护原则和目录示例。

## 一、方案结论

采用“分布式维护、统一发现、按任务消费、持续治理”的知识体系：

1. **代码仓承载版本耦合知识**：接口契约、现行行为规格、本服务架构、ADR、Runbook、Agent 作业指令，与实现一起评审、演进。
2. **中心知识仓承载共享知识**：业务术语、跨服务流程、组织规则、知识导航、经确认的共性经验。
3. **一项事实只有一个权威来源**：中心仓可以索引代码仓，但不再人工维护相同正文；需要镜像时，明确源、版本、同步方式，镜像不可独立编辑。
4. **区分现行知识、进行中变更、历史材料**：不能只把所有文档统称为 SPEC，更不能让 Agent 默认混用。
5. **先建立治理语义，再决定目录与工具**：最小团队可只使用 Git 与轻量目录；并行变更多、Agent 使用重时，再考虑显式 delta 和归档工作流。

核心判断不是“文件名叫什么”，而是：**它由谁负责、适用于什么范围、随什么变化、当前能否作为执行依据。**

## 二、先统一知识类型

| 类型 | 回答的问题 | 主要内容 | 推荐权威位置 |
|---|---|---|---|
| 业务知识 | 为什么需要、业务上是什么 | 术语、规则、边界、跨服务主流程 | 中心仓；单服务独有规则也可在代码仓 |
| 现行 SPEC | 当前系统应表现为什么 | 需求规则、边界条件、验收场景 | 代码仓，按能力组织 |
| 需求提案 Proposal | 本次为什么改、改哪些范围 | 目标、非目标、收益、影响面 | 变更所属仓；跨仓提案可在中心仓 |
| 设计文档 Design Doc | 本次具体怎么实现 | 数据、接口、事务、兼容、迁移、风险 | 通常在代码仓的变更目录 |
| ADR | 为什么选择某个重要方案 | 背景、备选、决定、后果 | 决策影响范围对应的仓 |
| 接口契约 | 调用方如何交互 | 路径、字段、错误码、兼容约束 | 服务代码仓，例如 OpenAPI |
| Runbook | 运行中如何检查、处置、验证 | 触发条件、只读诊断、受控操作、回滚、升级 | 服务代码仓；跨服务应急流程可在中心仓 |
| Agent 作业指令 | 在这个项目里如何工作 | 构建、测试、规范、权限边界、导航 | 代码仓 `AGENTS.md` |
| 历史变更档案 | 当时改了什么、为何、如何验收 | 提案、设计、delta、任务、证据 | 原变更所属仓的 archive，或 Git 历史 |

### ADR 与 Design Doc 的关系

ADR（Architecture Decision Record，架构决策记录）不是完整设计文档的替代品。一个设计文档可能产生零个、一个或多个 ADR。只有重要、长期影响后续工作的决策值得单独记录。

ADR 推荐包含：状态、背景、决定、备选、后果、相关链接。决策被替代时保留原文，标记 `superseded` 并链接新 ADR；不要悄悄改写历史理由。

### Runbook 的安全边界

Runbook 不只是“故障后执行哪条命令”，还必须说明前置条件、权限、影响范围、停止条件和验证方式。先只读排查，再经授权执行变更。不得把重启当成连接池或数据库锁问题的通用解法，也不得写不存在的 `npm run rollback` 让 Agent 猜着执行。

## 三、承载划分原则

### 3.1 四个判断问题

- **跟谁一起变？** 随实现、依赖或发布变化的，优先在代码仓。
- **对谁有效？** 跨服务、跨团队有效的，优先在中心仓。
- **谁能确认正确？** 明确服务 owner 或领域 owner，不能只有文档创建人。
- **使用时是否必须匹配版本？** 必须匹配的，绑定 tag、commit、环境或版本范围。

“编译能发现错误就放代码仓”只能是辅助判断：架构决策、Runbook 即使放在代码仓，也不一定能靠编译发现错误。业务规则同样可能需要和代码一起版本化。

### 3.2 中心仓不等于全文搬运仓

中心仓承担共享内容的权威维护与全局导航。代码仓内容可以被统一检索服务索引，但**统一索引不等于改变权威来源**。

跨仓链接在实际项目中应使用可解析的仓库 URL；需要复现历史时链接到 commit/tag。本文目录树中的相对位置仅用于示意，不代表两个独立 Git 仓可以直接用本地相对路径互相访问。

## 四、最小项目目录与文件职责

以下是参考结构，不是要求一次性创建全部文件。`src/`、测试和配置仅用于交代上下文，本文不提供可运行应用。

```text
knowledge-example/
├── center-kb/                         # 独立中心知识仓
│   ├── README.md                      # 入口、知识规则与维护方式
│   ├── global-business-map.md         # 全局领域与仓库导航
│   ├── domains/
│   │   └── order/
│   │       ├── index.md               # 订单领域主题导航
│   │       ├── glossary.md            # 订单、SKU、可用库存等术语
│   │       └── order-flow.md          # 业务主流程、边界及服务映射
│   ├── standards/
│   │   └── engineering.md             # 跨项目工程与安全基线
│   └── lessons/
│       └── README.md                  # 经确认的共性经验索引，初期可不建
│
└── order-service/                     # 产品代码仓
    ├── README.md                      # 项目入口与本地启动说明
    ├── AGENTS.md                      # Agent 作业指令及知识加载顺序
    ├── src/                           # 实现
    ├── tests/                         # 行为与契约验证
    ├── api/
    │   └── openapi.yaml               # HTTP 接口权威契约
    └── docs/
        ├── architecture.md            # 当前架构
        ├── runbook.md                 # 当前运行维护手册
        ├── adr/
        │   └── 001-local-transaction.md
        ├── specs/
        │   └── order-create.md        # 当前有效的下单行为规格
        └── changes/                   # 有真实变更需求时再创建
            ├── add-idempotency/       # 进行中的“下单幂等”变更
            │   ├── proposal.md
            │   ├── design.md
            │   ├── delta.md           # 可选；也可直接用 Git diff
            │   └── tasks.md
            └── archive/               # 历史变更材料，不是现行规格
                └── <date>-<change-id>/
```

`docs/changes/` 及其 `delta.md` 是本方案的自定义轻量约定，**不是 OpenSpec 或 Spec Kit 的原生目录规范**。最小团队可以先不用 `changes/`，通过 PR 描述、SPEC diff 和 Git 历史管理。

### 4.1 中心仓每个文件主要写什么

| 文件 | 主要内容 | 不应放什么 |
|---|---|---|
| `README.md` | 目录说明、owner 规则、评审/复核方式、状态定义 | 各服务部署命令副本 |
| `global-business-map.md` | 领域、服务、仓库 URL、负责人、领域入口 | 大段实现细节 |
| `domains/order/index.md` | 主题链接、适用范围、相邻领域、待补主题 | 复制全部子文档 |
| `glossary.md` | 业务术语、易混概念、统一口径 | 同名 API 字段的重复契约 |
| `order-flow.md` | 下单业务目标、主流程、边界、服务分工、指向 SPEC/契约的链接 | 逐行描述实现，或复制现行 SPEC 全文 |
| `standards/engineering.md` | 跨仓测试、评审、安全等最低要求 | 单服务特有启动命令 |
| `lessons/README.md` | 经验证的经验摘要及原始复盘链接 | 未确认聊天结论直接提升为规则 |

### 4.2 代码仓每个文件主要写什么

| 文件 | 主要内容 | 更新触发 |
|---|---|---|
| `README.md` | 服务职责、真实可执行的安装/启动/测试方式、文档导航 | 环境或使用方式变更 |
| `AGENTS.md` | 先读什么、怎么运行验证、变更需更新哪些文档、操作禁区 | 工具链与作业规则变化 |
| `api/openapi.yaml` | 请求/响应、错误码、认证、幂等字段等接口定义 | 接口变更 |
| `architecture.md` | 当前模块、数据边界、依赖、事务边界、ADR 链接 | 架构调整 |
| `runbook.md` | 监控信号、诊断步骤、受控操作、验证/回滚、联系人 | 发布方式、监控、故障经验变化 |
| `adr/001-*.md` | 为什么在当前约束下选择本地事务，以及适用限制 | 新决策或旧决策被替代 |
| `specs/order-create.md` | 当前下单规则、失败行为与验收场景 | 行为变更完成并确认后 |
| `changes/*/proposal.md` | 本次目标、非目标、业务动机、影响面 | 变更范围调整 |
| `changes/*/design.md` | 技术实现、数据迁移、兼容性、失败处理、风险 | 实施中发现方案需修正 |
| `changes/*/delta.md` | 相对基线新增/修改/删除哪些行为 | 拟议行为调整；可选 |
| `changes/*/tasks.md` | 实施任务、验收项、验证结果和证据链接 | 研发进展与验收 |

`llms.txt` 可作为额外导航，但对这个最小项目不是必需；不能假设 Agent 会自动读取。先让 `README.md` 和 `AGENTS.md` 的导航清晰即可。

## 五、设计文档与 SPEC 的生命周期

### 5.1 三种语义必须分开

| 语义 | 含义 | 默认用途 |
|---|---|---|
| 现行基线 | 指定版本当前有效的行为和约束 | 理解系统、排查问题、设计新变更 |
| 进行中变更 | 计划相对基线改变的内容 | 仅在对应需求任务中加载 |
| 历史档案 | 当时的提案、讨论、实现与验收证据 | 追溯原因，不直接当现行规则 |

SPEC 不必全部“冻结成 v1.0、v1.1 文件副本”。默认使用**稳定路径 + Git 版本历史**维护现行规格；评审基线可以用 commit/PR、tag 固定。只有监管、审计或外部签署需要不可变交付包时，再制作签署快照。

草稿也不必先放中心仓再复制进代码仓。单服务需求可以从第一天就在代码仓的变更目录评审；跨仓需求可以在中心仓维护总体提案，再链接各服务实施变更。

### 5.2 推荐流程

```text
识别需求
  → 建立提案与影响范围
  → 定义预期行为 / 必要时编写 delta
  → 设计与评审
  → 实现、测试，发现变化时同步修订变更材料
  → 确认与目标版本一致
  → 将已接受的行为合入现行 SPEC，更新契约/架构/Runbook
  → 记录 PR、commit、发布版本及验证证据
  → 将变更材料归档，更新中心仓受影响的共享知识或导航
```

评审通过不等于已经生效。推荐区分 `draft → approved → implementing → verified → archived`，取消的变更标 `cancelled`。这是本方案建议的变更状态，不是工具内置状态。

归档完成也不等于已在所有环境上线。可记录 `merged_commit`、`release_tag`、`deployment_status`；按仓库版本描述的基线不能直接被当成生产运行状态。多发布线按各自分支/tag读取知识。

## 六、delta / archive 是否需要

### 6.1 建议结论

**建议保留“现行 / 变更 / 历史”的区分，不强制建立独立 delta 目录，也不强制引入任何工具。**

| 情况 | 合适做法 |
|---|---|
| 单人、小项目、低频小变更 | 直接更新现行 SPEC，用 PR/Git diff 表达增量，用 Git 保存历史 |
| 需求持续多轮评审、需要设计和任务协同 | 增加每需求一个 change 目录，必要时单独写 delta |
| 多人/多 Agent 并行、频繁改同一能力 | 增加显式 delta、基线引用、冲突检查、合并与归档流程 |
| 需要规范检查、自动同步规格、统一 Agent 流程 | 对 OpenSpec / Spec Kit 做试点，再选择工具 |

没有必要同时维护 `active/`、`frozen/`、`delta/`、`archive/` 四套重复正文。delta 是相对某个基线的变更语义，不一定叫 `delta/` 目录。

### 6.2 两类工具实践不能混同

**OpenSpec** 明确区分当前规格与变更材料。官方入门文档示例为：

```text
openspec/
├── specs/<domain>/spec.md                  # 当前规格
└── changes/
    ├── <change-name>/
    │   ├── proposal.md
    │   ├── design.md
    │   ├── tasks.md
    │   └── specs/<domain>/spec.md          # delta spec
    └── archive/<date>-<change-name>/       # 历史变更
```

delta 使用 `ADDED / MODIFIED / REMOVED Requirements` 表达行为变化；同步/归档流程把变化应用到主规格，并保存变更历史。官方示例归档在 `openspec/changes/archive/`，不是此前对话中的 `openspec/archive/`。

**GitHub Spec Kit** 强调由规格驱动规划、任务、实现和验证等结构化过程。不能因为它有 `spec/plan/tasks` 产物，就声称它“天然等同于 OpenSpec 的 delta + archive”。具体目录、命令与扩展能力应以所采用版本为准。

本文借鉴的是分层思想，不要求同时采用两套工具。若正式使用其中一个工具，应服从该工具的文件格式与命令约定，而不是将本文自定义目录冒充原生格式。

### 6.3 下单幂等变更示例

基线：`docs/specs/order-create.md` 描述当前下单行为。

本次拟议变更：同一个幂等键与相同参数不能产生多笔订单。轻量 delta 可以写为：

```markdown
# 变更：创建订单增加幂等控制
基线：<基线 commit> 的 docs/specs/order-create.md
状态：draft，评审通过前不作为现行行为

## ADDED
- 同一用户、相同幂等键与相同参数的重复成功请求，返回同一订单。
- 相同幂等键但请求参数不同，返回冲突错误，不创建新订单。

## 待确认
- 幂等键有效期。
- 首次请求仍在处理中时，重复请求的响应策略。

## 验收
- 并发相同请求不产生重复订单。
- 不同用户的幂等键互不影响。
- 参数冲突不会改变已有订单。
```

设计文档说明幂等键存储、唯一约束、事务边界、并发处理、有效期与清理策略；接口定义仍以 `openapi.yaml` 为准。未决问题解决后再批准实施。

完成后：将完整的已接受规则与场景合入现行 SPEC，而不是把 `ADDED/MODIFIED` 标记原样堆进主规格。更新接口与测试，记录证据，再归档 change 目录。下个需求默认读现行 SPEC，不逐个重放全部 delta。

### 6.4 归档门禁

归档前确认：

- 行为与实现一致，必要测试通过；未完成项明确延期或取消。
- delta 已同步到对应版本的现行 SPEC，契约/架构/Runbook 已按需更新。
- 并行变更如修改同一要求，已检查基线漂移并解决语义冲突。
- 存在 PR、版本或 commit、验收证据链接及责任人。
- 历史材料标明状态、适用版本及替代关系，不自动提升为共享规则。

archive 默认不参与日常回答召回；用户追溯历史时再定向检索。若需要统一检索历史，也要使用独立范围或状态过滤，并继承源仓权限。不能仅靠“搬入 archive 目录”保证 RAG 不误用。

## 七、知识如何消费

### 7.1 关联要广，执行上下文要窄

关联的目的是发现影响面；消费的目的是为当前动作提供必要依据。被关联的文档不必全文塞入 Prompt。

| 阶段 | 优先消费 | 按需关联 |
|---|---|---|
| 需求理解 | 需求目标、业务术语、边界、现行 SPEC | 历史相似需求、相关领域 |
| 方案设计 | 现行 SPEC、架构、有效 ADR、接口契约 | 跨服务流程、历史事故 |
| 编码 | AGENTS.md、本次批准变更、相关代码与测试 | 模块摘要、库使用示例 |
| 验证 | 验收场景、契约、测试与兼容要求 | 环境说明、历史缺陷 |
| 发布排查 | 目标发布版本的 Runbook、变更风险、实际环境信号 | 原始复盘和历史设计 |

### 7.2 推荐读取规则

1. 根据任务识别领域、仓库、目标版本、权限。
2. 从全局或仓内导航定位主题；已知文件时直接读取，不必总做全库检索。
3. 查询“当前行为”时，优先现行 SPEC、有效契约和实现证据；查询“本次目标”时，读取批准的变更材料。
4. 只加载必要章节、相关代码与场景；复杂调用关系再补充结构化检索。
5. 发现规格、设计、契约、代码冲突时显式报告并请 owner 确认，不能让模型悄悄选择一个版本。

检索流程可采用关键词 + 向量混合召回，再重排、去重、适度扩展父章节。**权限过滤、版本范围、状态筛选是硬约束，相似度分数不是事实可信度。** 没有证据时应说明不确定或请求确认；温度为 0 也不能保证无幻觉。

## 八、知识治理：更新、老化与责任

### 8.1 最小元数据

对共享 wiki / 现行知识，可按需要采用：

```yaml
---
id: order-create
owner: order-team
status: active
scope: order-service
last_reviewed: 2026-11-11
review_due: 2027-02-11
applies_to: "<明确的版本或分支范围>"
sources:
  - "<可解析的证据链接>"
superseded_by: null
---
```

上述值与周期为示例。代码仓原生文件不必全部强加同一套 Frontmatter；Git 元信息、ADR 头部、契约版本等可以共同提供治理信息。变更工单与知识文档使用不同状态体系，避免用 `mature` 混淆“评审通过”与“已经上线”。

### 8.2 判断老化与处理方式

| 发现的信号 | 正确解释 | 动作 |
|---|---|---|
| 接口、代码路径、部署方式变化 | 相关知识可能失配 | 变更影响分析，触发 owner 复核 |
| 复核日期超期 | 待确认，不等于内容必错 | 标记需复核，按风险决定是否限制消费 |
| 明确被新规则替代 | 对原范围可能不再有效 | 标记 superseded，指向替代内容 |
| 用户多次纠错、按文档操作失败 | 潜在知识缺陷，也可能是环境/检索问题 | 归因后修订，必要时暂停高风险操作指引 |
| 低频或零访问 | 不代表无价值，可能是灾难恢复手册 | 结合关键性决定保留、合并或调整导航 |
| 适用版本已停服 | 可转历史范围 | 归档，遵守保留与审计要求 |

不使用“漂移一个 minor 版本即失效”之类统一规则。根据文档依赖的实体和实际兼容性判断；同样，SQLite 锁竞争与跨服务 Saga 是不同问题，不能把 Saga 当作数据库并发问题的直接解决方案。

### 8.3 嵌入研发流程

- PR：声明行为、接口、架构、运行方式是否变化，并链接需同步的知识。
- 发布：校验知识适用版本，检查链接、示例与 Runbook；必要时触发增量索引。
- 故障复盘：回流经确认的“现象—条件—根因—处置—验证”，而不是未经审核的临时建议。
- 定期复核：高风险且易变的优先；周期由 owner 与风险确定，不要求所有内容统一季度更新。

## 九、知识如何进化：准确性与成本一起优化

### 9.1 入库前处理

- 保留原始来源、章节层次、表格与条件，按权限清洗敏感内容。
- 文档按完整主题/规则分块，代码按结构边界解析。
- 为大仓库按需生成模块摘要、依赖关系、导航；摘要保留源版本与证据。
- 摘要、向量和图谱属于派生产物，不能取代原始规格或被直接标为事实。
- 源变化后增量更新受影响内容；同步删除、权限变化、替代关系及缓存失效。

### 9.2 检索与使用后处理

- 先过滤范围与权限，再召回、重排和去重；按需读取相邻条件。
- 压缩上下文不能删除否定条件、例外、安全约束和版本信息。
- 对重要结论展示来源；信息不足则追问或转 owner。
- 缓存包含版本、权限、状态等维度，防止复用过期或越权上下文。

预生成、重排、图谱等都有建设与运行成本，不保证一律更便宜。最小项目先用良好的目录、文本搜索与显式链接，确有瓶颈再加复杂检索。

### 9.3 用行为数据改进，但不自动把行为当真相

记录必要的任务、检索结果、源版本、引用、反馈与验证结果；涉及员工行为、源代码或敏感内容时，遵循最小采集、权限、脱敏与保留期限。

| 现象 | 可能原因 | 下一步 |
|---|---|---|
| 高频问题无可用来源 | 知识缺失或索引漏收 | 确认后补知识或修索引 |
| 来源存在但找不到 | 路由、词汇、切分或召回问题 | 优化别名、导航和检索 |
| 找到但版本不匹配 | 版本元数据或过滤有误 | 修范围与索引 |
| 来源正确但答案错误 | 模型理解或上下文压缩问题 | 调整组装与验证 |
| 采纳后测试失败 | 知识、实现、环境皆有可能 | 归因，避免直接认定知识过期 |

评测集取自真实任务并经人工确认，包含常见题、边界题、旧版本题、权限题与无答案题。衡量检索召回、答案正确性与证据一致性、任务完成质量，同时监控 token、延迟、总成本和人工复核时间。反馈先进入候选改进，经评审与回归验证后再发布，避免自我强化错误。

## 十、建议落地顺序与验收

### 阶段一：最小承载

建立中心导航、业务术语与流程；代码仓建立 README、AGENTS、现行 SPEC、契约、架构与 Runbook。只记录真实可验证内容；没有实现的命令和路径标注为示例，不假称可运行。

验收：新人或 Agent 能找出服务入口、当前行为、测试方法、变更负责人，且不会把草案当作现行规则。

### 阶段二：跑通一次变更

以“下单幂等”为试点，视复杂度增加提案、设计、任务与可选 delta；更新基线后保存历史证据。借此决定是否需要显式 change/archive 目录，而不是先建空目录体系。

验收：能回答“改前是什么、这次改什么、如何验证、哪个版本生效、旧材料在哪里”。

### 阶段三：索引与持续治理

有实际跨仓发现或上下文成本问题时，再引入统一检索、版本与权限过滤、增量同步、反馈评测。需要工作流自动化时，试点并固定 OpenSpec 或 Spec Kit 的工具版本。

验收：现行检索不混入历史/未批准变更；来源变化能够传播到索引；质量和成本改善可由评测说明。

## 十一、待团队决定的事项

以下均为待决项，不代表对话中已批准：

1. 是否使用独立中心 Git 仓，还是用现有文档平台作为共享知识权威来源。
2. 是否采用显式 change/delta/archive，还是暂用 PR 与 Git 历史。
3. 是否引入 OpenSpec 或 Spec Kit；如引入，选择哪个版本及工作流。
4. 哪些文档属于必需门禁，谁是 owner，如何处理跨仓评审。
5. 是否建设统一检索，以及权限、审计、行为采集的边界。

默认起点：**保留最小文件集合和单一权威来源，用一次真实变更验证，再增加机制。**

## 十二、对前序讨论的校正与参考

本方案取代前序讨论中以下过强或不准确的说法：

- 并非所有草稿都应在中心仓，评审后也不必复制一份冻结版进代码仓。
- 现行 SPEC 需要稳定入口；不推荐只剩 active/frozen/archive 而没有现行完整规格。
- Spec Kit 与 OpenSpec 不能视为同一种 delta/archive 工作流。
- archive 目录本身不保证 RAG 安全，必须配套状态、版本与权限过滤。
- ADR、Runbook、业务规则的位置取决于影响范围，不是绝对“必须跟单个代码仓”。
- 之前创建的 `example-kb-demo/` 是文档示例骨架，未提供完整实现、包脚本或 CI，不能称为可运行项目；其中演示命令、路径和关联内容需要实施前核验。
