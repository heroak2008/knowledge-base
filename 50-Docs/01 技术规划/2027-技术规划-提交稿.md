# 2027 技术规划 · 提交稿

> 在 v3 发散稿基础上整理，每个方向只说清楚四件事：输入输出、做法、价值。KPI 暂不讨论，另文处理。
> 业界参考部分已于 2026-11-06 联网核实，附来源链接。

---

## 一、方向摘要

### 方向1：任务-知识路由器

- 输入：任务类型、场景标签、US 和代码上下文
- 输出：本次任务需要的知识清单，包括相关规范、案例和接口，每条都带引用标注
- 做法：把知识按场景打成标准包，每包含热知识和硬约束清单。不做全量治理，靠工作台埋点记录哪些知识被调用、有没有用，据此持续调整
- 价值：解决的是"知识在库里但用不上"这个问题，也是"让Agent配全"这个思路最直接的落点。方向2注入什么、方向4拿什么做校验，都从这里取材

### 方向2：隐式约束自动注入

- 输入：人写的关键差异，加上规约库里的编码规范、架构红线、接口版本、吞吐量纲默认值
- 输出：补全了通用约束的完整任务输入；另外在生成前一次性提出3到5个结构化澄清问题
- 做法：通用约束由 Agent 从规约里补，人只写差异部分。需求完整性门禁放在生成之前，问完就不再为需求返工
- 价值：承认输入永远不完备这个现实，把人的输入负担转移到平台侧。配准（方向1）之后紧接着就是注入，澄清轮次和返工都会减少

### 方向3：闭环2联邦互联（主线）

- 输入：需求、代码、测试、缺陷四个系统的存量数据和事件流
- 输出：跨系统 Connector 和 ID 映射表，全链路引用可追溯
- 做法：一季度先通需求到代码，二季度补测试和缺陷。只连不改，不动存量系统内部逻辑，全部在小网内闭环
- 价值：所有自动化闭环的前提。只连不改的方针控制了对存量系统的侵入。引用可追溯也是后面审计、计费归因、效能度量的数据基础

### 方向4：设计驱动的独立校验

- 输入：US 和设计文档作为正源；代码 Agent 的产出作为被校验对象
- 输出：从 US 和设计正推出来的验收用例集，以及两者冲突点清单，交给人裁决
- 做法：测试 Agent 和代码 Agent 用不同来源互相制约，解决"代码反推单测、自己考自己满分"的问题。人只裁决冲突，不做全量评审
- 价值：全自动闭环的可信度靠这个方向保证，否则自动化只是更快地出错。人的参与也从全程跟随压缩到只看冲突点

### 方向5：Token 可观测 + 计费 + 熔断

- 输入：任务和轮次级的调用流水，包括谁发起、跑了什么、消耗多少
- 输出：任务和轮次级账单、场景配额、超步数或超预算时的熔断动作
- 做法：统一埋点，成本归因到发起方和场景；配额加熔断两道闸；账单同时支撑收费分摊
- 价值：一份基建三处用：收费分摊要靠它记账，全自动失控要靠它刹车，效能证明（省人天对比花token）要靠它出数据。方向4放开全自动之前，这个方向必须先就位，明年 token 收费也指着它

### 方向6（底座）：单向供给链 + 运维安全

- 输入：大网侧的模型、依赖和镜像更新
- 输出：按月同步到小网的镜像（含 SBOM 和白名单）；小网权限隔离和全链审计日志
- 做法：大网到小网单向同步，小网闭环推理不回传，权限按场景隔离
- 价值：网络单向约束下唯一的供给通道，也是安全合规的底线。审计链同时服务方向4的决策回放和方向5的归因

### 方向7：缺陷根因聚类回流（新增）

- 输入：闭环2已经接入的缺陷库数据，包括缺陷描述、关联代码和需求、修复记录
- 输出：高频根因的聚类结果，以及据此起草的知识包更新（新案例或新的硬约束条目），人工审核后入库
- 做法：定期对缺陷库做根因聚类，高频根因自动起草知识包条目，人确认后入库，再经方向1路由到后续任务
- 价值：知识包由此能自己长起来，缺陷修过之后变成知识，知识再防住同类缺陷。成本低，因为数据和基建都是现成的，而且和闭环2主线咬合得很紧

### 方向8：Eval 回归门禁（新增）

- 输入：50 条 US 的 Eval 基线集；待发布的变更，比如模型升级、模板修改、路由器调参
- 输出：变更前后的基线对比结果，以及通过或回退的结论
- 做法：一季度建好基线后不只测一次。每次变更都强制跑回归，退化超过阈值就阻断发布。基线集随代表性任务滚动扩充
- 价值：防止改好一处、退化三处。基线本来就要建，加一道回归流程几乎不增加投入。方向6每月升级模型，尤其需要这道闸

### 方向9：模型分级路由（新增）

- 输入：方向5埋点沉淀的任务分级信息（任务类型、历史复杂度、失败率），加上各级可用模型清单
- 输出：每个任务分配到合适的模型，简单任务给小模型，复杂任务才用旗舰模型
- 做法：先按任务类型做静态分级，数据攒起来之后引入按失败率动态升级的规则。分级策略本身也要过方向8的回归验证，确认不伤质量
- 价值：单看一项的话，这里通常是省token空间最大的。小网算力自持，还能顺带错峰调度。方向5一季度就建可观测，正好接得上

## 二、业界可参考的项目与实践

### 知识路由 / 上下文配准（对应方向1）

| 项目/实践 | 可借鉴点 |
|---|---|
| Cursor（context engine + rules） | codebase 索引加 `.cursor/rules`，按路径和场景自动挂载规范（[Cursor Rules 文档](https://cursor.com/docs/rules)），和"场景知识包"思路几乎一样，规则文件格式和触发条件可以直接参考 |
| Aider（repo map + conventions） | 用 repo map 做选择性上下文注入而不是全量塞入；conventions 文件就是"热知识包"的极简形态 |
| Sourcegraph Cody | 企业级代码知识检索和上下文精度调优的工程经验 |
| Continue.dev / Cline | 团队级规范文件分层（全局/项目/场景）的组织方式 |

### 隐式约束 / 需求澄清（对应方向2）

| 项目/实践 | 可借鉴点 |
|---|---|
| GitHub Spec Kit | spec-driven development 的标准流程：先 spec、plan、tasks 再写码，其中"澄清问题清单"环节就是结构化门禁的现成参考（[官方文档](https://github.github.io/spec-kit/)；另见 [Thoughtworks Technology Radar](https://www.thoughtworks.com/en-us/radar/languages-and-frameworks/github-spec-kit)、[VS Magazine 报道](https://visualstudiomagazine.1105cms01.com/articles/2026/05/12/github-spec-kit-takes-off-as-antidote-to-piecemeal-vibe-coding.aspx)） |

| 通义灵码 / Trae / CodeBuddy | 国内厂商把企业编码规范注入生成环节的产品化做法，都有类似的"企业规则"配置 |

### 闭环 / 异源校验（对应方向3、4）

| 项目/实践 | 可借鉴点 |
|---|---|

| SWE-bench 及其衍生 | "从 issue 正推验证"的评测范式，方向4的设计驱动用例可以借鉴它的任务和验证构造方式 |

## 三、补充探索方向（讨论池）

> 对 5+1 的查漏，按质量、效率、用户体验、节流四个维度整理。其中三条已提升为正式方向（方向7、8、9），剩下八条留作后续讨论。

### 质量

1. 评审 Agent 化：合入前由独立 Agent 按规约和知识包做首轮评审，人只看高置信度的问题。和方向4是姊妹件，方向4管验收对不对，这条管过程合不合规，裁判基建可以共用。
2. 缺陷根因聚类回流：已提升为方向7。
3. Eval 回归门禁：已提升为方向8。

### 效率

4. 任务并行编排：优化 Agent Teams 的拆分、并行、汇合策略，独立模块并行生成，冲突前置检测。这是现有 SDD 加 Agent Teams 的深化。
5. Playbook / 模板市场：把各部门验证过的执行路径固化成模板，跨部门流通。和多部门薄试点天然配套，试点产物直接变成资产。

### 用户体验

6. 冲突裁决轻交互：方向4要求人只裁决冲突，那就得有配套的裁决界面，冲突并排呈现、一键采纳或驳回、结果回流。没有好的裁决界面，"人只裁决"会退化成人全程盯着看。
7. 引用可视化：知识清单、生成依据、跨系统追溯链都能在工作台里点开查验。这是自动化建立用户信任最主要的手段。
8. 个性化偏好记忆：按人和团队记住评审口味、常用澄清答案、惯用模板。办公场景尤其见效。

### 节流

9. 模型分级路由：已提升为方向9。
10. 上下文压缩与选择性检索：repo map 式的选择性注入，历史轮次摘要压缩，不搞全量上下文重放。和方向1同源，配准本身就是最大的节流。
11. 多级缓存：厂商侧的提示前缀缓存、同类问题的语义缓存、知识包和检索结果缓存。纯工程收益，风险低，命中率可以和方向5的账本联动度量。
